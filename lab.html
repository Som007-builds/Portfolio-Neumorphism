Tools in the featured projects

Stack / Used, not just studied

The concrete tools behind Axion, Orion, and Indigent. These are working stacks I can discuss and point to in the source—not a claim of expert-level depth in every one.

01

Backend & data

Python and FastAPI services with REST request/response boundaries. SQLite (WAL) and DuckDB for operational data, with ingestion and analysis separated from the request thread.

Seen in: Orion (DuckDB analytics), Indigent (SQLite control plane).

02

Data & retrieval

A Neo4j property graph for claims and a ChromaDB vector index in Axion; Qdrant for local vectors in Indigent. Embeddings, semantic retrieval, and provenance that ties an answer back to its source.

Seen in: Axion (graph + vectors), Indigent (local Qdrant RAG).

03

AI & models

Integrating hosted LLM APIs and local models through Ollama, treating model output as a proposal, and combining deterministic rules with ML-assisted analytics such as peer-relative anomaly detection and feature attribution.

Seen in: Axion (relation / gap reasoning), Orion (rules + ML), Indigent (local agent loop).

04

Isolation & assurance

Policy validation before every tool call, fail-closed defaults, Docker sandboxes with --network=none and read-only filesystems, append-only audit ledgers, and air-gapped operation.

Seen in: Orion (air-gapped, ledger), Indigent (policy validator + sandbox), and the Arbiter design.

Building the foundation

Learning / Ongoing

01

C & Java

Learning how programs use memory and how to structure them beyond a single file. C makes pointers, allocation, and resource ownership explicit; Java offers a different way to think about objects, interfaces, and responsibilities.

Focus: memory management, object-oriented programming, and understanding design patterns before reaching for them.

02

Python & DSA

Building fluency with Python alongside data structures and algorithms. The aim is to understand why a representation or algorithm fits a problem, rather than treating a passing solution as the end of the exercise.

Focus: choosing data structures, reasoning about complexity, and testing edge cases with small, understandable programs.

03

Machine learning

Working toward the foundations behind model integration: what data a model needs, how to evaluate its output, and where inference belongs in a larger application. Local models are a practical way to explore those questions without hiding the runtime behind a hosted API.

Learning direction: Python-based ML tools, evaluation, and the hardware constraints of local inference. This is a learning track, not a claim of production ML expertise.

04

Systems architecture

Practicing the habit of tracing a request across components. Where is the data stored? Who is allowed to read it? What happens when the network or a dependency fails? Sketching those flows helps expose assumptions before they become code.

Focus: interfaces, trust boundaries, failure paths, and keeping the design small enough to test. Architecture is something I’m learning through the projects, not a shortcut around implementation.

Questions worth exploring

Concepts / Not products

These are starting points for research. Neither has a validated feasibility score, a finished application, or a deployment behind it.

Concept 01

Financial Literacy App

A vernacular-first financial education app for Indian youth. The idea is to explain everyday decisions—saving, budgeting, borrowing, and understanding risk—in language that feels accessible rather than institutional.

AI-assisted explanations are a possibility, not the starting assumption. The first questions are which learners need help, which languages and formats work for them, and how educational content could be checked for accuracy without drifting into personalized financial advice.

Next question: can a small set of clear, locally relevant lessons be useful before any AI feature is added?

Concept 02

Industrial Automation Expansion

An exploration of whether ideas from simple local monitoring and scheduling could help small Indian manufacturing units with basic equipment visibility.

This would not be a small consumer setup scaled up unchanged. Industrial equipment introduces different electrical loads, safety obligations, maintenance needs, and failure consequences. Understanding an actual workshop’s workflow would come before selecting hardware or promising automation benefits.

Next question: is there a narrow monitoring problem worth solving without taking control of safety-critical equipment?

From a question to a test

Working approach

Start with the smallest useful behavior. Draw the data flow, name the assumptions, and find something observable to test. A privacy layer needs evidence that sensitive data stays behind its boundary; an automation system needs safe behavior when a connection fails. A convincing diagram is only the beginning.
