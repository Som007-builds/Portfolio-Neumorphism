Foretyx / Arbiter

Venture / AI security, governance & privacy gateway · Design & feasibility

Foretyx is my venture; Arbiter is its proposed product: a gateway that makes the decision to share data with a model explicit, inspectable, and policy-aware.

Design documented; product implementation not independently verified. No matching public source or runtime demonstration was established in this review.

Problem

Adding an AI model to an application creates another boundary for sensitive data. Customer records, employee information, and financial details should not reach an external model simply because they happen to be available to the application.

Approach

Arbiter would sit at an application’s model-call boundary, combining authorization with payload minimization. The first scope is one deliberately integrated application and one model adapter—not automatic protection for every AI tool an organization uses.

Proposed request lifecycle

  1. Intercept: accept a bounded request with trusted identity, role, purpose, and destination context from the application.
  2. Evaluate policy: apply a versioned allowlist for role, data, and model destination. Reject missing identity, unknown policy, or denied requests before any model call.
  3. Minimize: detect candidate PII, redact disallowed fields, and use scoped pseudonyms only where continuity is needed. Recheck the transformed request; uncertain cases stop.
  4. Call the model: send only the approved payload to the approved local or hosted adapter with a timeout. Return the response through the gateway; response inspection is a separate planned boundary.
  5. Audit & fail safely: record decision metadata for allow, deny, and error paths. Policy/filter failure stops forwarding; model timeout returns a controlled error with no silent provider fallback.

Proposed: request interception · Policy enforcement · PII redaction · Scoped pseudonymization · Metadata-only audit

Design decisions & tradeoffs
Detection accuracy vs. latency
Rules offer predictable cost but miss context; semantic detectors may improve coverage at additional latency and with false positives. Measure missed PII, over-redaction, and gateway overhead separately from model time.
Redaction vs. pseudonymization
Removal loses context. Stable pseudonyms preserve relationships but remain linkable and are not anonymization; keys, scope, retention, and access require explicit decisions.
Local vs. hosted processing
Local detection limits external disclosure but adds hardware and maintenance costs. Hosted detection itself crosses a data boundary; it must not receive raw sensitive data by default.
Fail-closed vs. availability
The proposed default is fail-closed on identity, policy, filtering, or required-audit failure, even if that interrupts a task. Fail-open would favor availability but permit unreviewed disclosure; it is not the default or a hidden fallback.
Policy & audit governance
Version policies, reject stale/unknown rules, and restrict who can change them. Log request ID, policy version, decision/reason code, destination alias, duration, and redaction counts—not prompts, responses, detected values, or raw identity. Limit access and retention; metadata can still be sensitive.

These are proposals, not production controls. A gateway cannot guarantee perfect detection, prevent all re-identification, or establish legal/regulatory compliance on its own.

Next milestone / Synthetic-data gateway

Build one policy evaluator, one deterministic redactor, a stub model adapter, and a metadata-only audit sink. Use fictional records only; keep real customer data out of the first prototype.

Future acceptance criteria—not test results: a permitted clean request reaches the stub once; a denied role/destination reaches it zero times; synthetic PII is removed from captured outbound payloads; missing identity, malformed input, stale policy, filter errors, and timeouts produce controlled failures. Audit-write failure must block forwarding. Verify allow/deny/error audit events contain no payload or sensitive fixture values.

AI Browser Chatbot

Local inference / Browser-based interface · Design documented

A proposed browser chat interface for an explicitly selected local model, with page context added only after permission. The goal is a clear data boundary, not a claim to replace every cloud assistant.

Design documented; implementation not independently verified. No matching chatbot source, working extension, or demo was established.

Problem

Cloud assistants are convenient, but sending a question and its supporting context to a remote service is not always the right tradeoff. Local models offer another route, although installing and using them still takes some setup.

Approach

The proposed HTML/JavaScript UI would keep conversation state in the browser and send requests to Ollama on the same machine. Inference would run in Ollama, not inside the browser. DeepSeek or Llama variants are model candidates, not verified project dependencies.

Intended request lifecycle

Choose a downloaded local model → compose a prompt → optionally preview and approve selected page text → send bounded conversation history to http://localhost:11434/api/chat → render response text safely. Cancellation, runtime-unavailable errors, and timeouts should leave the conversation recoverable without silently switching to a cloud provider.

A browser extension is a planned integration option, not an implemented feature. It would need narrow permissions, explicit context selection, a visible preview, and no automatic collection from every open tab.

Proposed: HTML / JavaScript · Ollama · Local model selection · Permissioned page context

Setup outline & configuration decisions

This is a proposed integration checklist, not verified repository setup instructions.

  1. Prerequisites: a supported Windows, macOS, or Linux machine, a modern browser, disk space for model downloads, and sufficient RAM/VRAM for the chosen model and context window.
  2. Follow the official Ollama quickstart to install the runtime and download a model explicitly intended for local execution. Check that model’s license, size, quantization, and task quality; start small.
  3. Use the official API reference to verify a local request before browser integration. A loopback endpoint alone does not prove the selected model is local: Ollama also supports cloud models.
  4. The future UI should configure model ID, loopback API base, bounded history/context, streaming choice, and request timeout. Restrict allowed browser origins as needed; do not expose the runtime publicly or broadly disable browser security to bypass an origin error.
Model quality vs. device limits
Model size and context compete for memory. Measure quality on a small fixed prompt set and record time-to-first-token, completion time, and memory on named hardware; no measurements are available yet.
Local inference vs. a fully offline workflow
A downloaded local model can infer without a hosted provider. Downloads, new web pages, remote UI assets, fonts, telemetry, or a selected cloud model can still use the network. This portfolio itself loads Google Fonts; it is not the chatbot runtime.
Context convenience vs. exposure
Page text is untrusted input and may contain sensitive data or prompt injection. Preview, minimize, and require consent; do not grant generated answers authority to execute actions. Render answers as text and make clearing history explicit.

Testing roadmap / One local conversation

Future acceptance criteria—not results: send one synthetic prompt to a confirmed local model; verify the selected model and endpoint, successful response, cancellation, missing model, unavailable runtime, timeout, and denied origin. Confirm page context is absent without approval and cleared history is not resent.

Inspect browser and runtime network traffic separately before any offline/privacy claim. Test safe display of HTML-like model output and check that no cloud fallback occurs. Hardware, storage, electricity, and machine security remain real costs.

Smart Home Automation

Hardware concept / Local control & scheduling · Feasibility unverified

A concept for an affordable local household-control hub: prove safe manual control and recovery first, then investigate scheduling and usage insights.

Concept only in the reviewed evidence. No hardware photos, firmware, PCB design files, bill of materials, or working installation were verified.

Problem

Household appliances often sit behind separate controls and disconnected automation products. For Indian homes, an affordable central system could make everyday control simpler and make usage patterns easier to understand—without requiring every device to depend on a cloud service.

Approach

The proposed design would combine manual control and schedules in one local hub for Indian homes. Usage monitoring would require separately selected and validated sensing hardware; relay state alone does not measure energy. Prediction and local inference are later research options, not delivered features.

Proposed control lifecycle

A mobile UI would send an authorized command over the home LAN to an SBC hub. The hub would validate it, send a WiFi command to a planned relay node, and wait for acknowledgement before showing confirmed state. A timeout should show unknown/unreachable—not a false success. Manual override, boot states, and recovery after WiFi/power loss must be defined before appliance control.

An SBC is the initial direction; a custom PCB is a possible later step after requirements and low-voltage bench validation, not evidence of a fabricated board.

Planned: SBC hub · WiFi nodes · Relay control · Mobile UI · Scheduling

Constraints, design decisions & testing roadmap
Budget target, not a quoted build
Under ₹10,000 is an aspirational household-setup target. There is no verified BOM or fixed device count; enclosure, power supply, sensing, protection, and qualified installation costs must be scoped before feasibility can be claimed.
Local control vs. operational responsibility
A LAN-first path reduces cloud dependence but still depends on hub, router, and node availability. Pairing/authentication, stale commands, acknowledgements, recovery, and manual override need testing. A safe state depends on the appliance; one universal “off” rule is insufficient.
Simple schedules before prediction
Deterministic schedules are easier to inspect and debug. Local inference adds compute and validation cost. No measured energy savings, control latency, reliability, or validated budget is available.

Future acceptance criteria—not test results: begin with one low-voltage indicator/load and one node, not household mains. Verify authorized commands, rejection of unauthorized/replayed commands, acknowledgement versus unknown state, manual override, schedule persistence, node reboot, and WiFi/hub/power-loss recovery. Define appliance-specific safe behavior with qualified electrical review before any mains prototype.

Only after that bench milestone: publish the firmware revision, real build photos, scoped BOM, and repeatable measurements. Evaluate energy use against a defined baseline with suitable metering; do not infer savings from schedules alone. Industrial expansion would require a separate safety and requirements process.

Next milestone / One safe bench node

Select a hub/node interface and document a low-voltage test plan with clear command, acknowledgement, timeout, and recovery states. Defer custom PCB design and prediction until the simplest control loop is demonstrated.
