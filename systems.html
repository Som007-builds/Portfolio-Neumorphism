SYSTEMS.

Three problems I’m working through: protecting data around AI, running models locally, and making household automation more accessible. The architecture, the constraints, and what still needs proving.

01

Foretyx

AI privacy middleware / Early design & feasibility

Problem

Adding an AI model to an application creates another boundary for sensitive data. Customer records, employee information, and financial details should not reach an external model simply because they happen to be available to the application.

Approach

Foretyx explores a privacy layer between an application and its AI provider. The idea is to combine PII filtering, anonymization, and access control so that the application sends only the information a particular task and user are permitted to expose.

Architecture

The proposed flow starts with identity and role context. A policy engine decides which data and model destinations are allowed; a PII filter then removes or anonymizes sensitive fields before an approved request is forwarded. An audit record would capture the decision without copying sensitive payloads into logs.

Privacy engineering · PII filtering · Anonymization · Access control

Current status

Early design and feasibility work, not a deployed enterprise service. I’m defining the privacy primitives and integration boundaries, with Indian SaaS and consumer applications as the intended context. Open to collaborators who want to question the design.

What needs proving

Filtering can miss PII; anonymization can remove useful context or leave re-identification risks. Policy accuracy, added latency, safe logging, and failure behavior need testing. Middleware also needs deliberate application integration—it cannot make an existing system compliant by itself.

02

AI Browser Chatbot

Local inference / Browser-based interface

Problem

Cloud assistants are convenient, but sending a question and its supporting context to a remote service is not always the right tradeoff. Local models offer another route, although installing and using them still takes some setup.

Approach

A straightforward HTML and JavaScript chat interface talks to Ollama on the same machine, using local DeepSeek or LLaMA models. The browser handles the conversation; the model runtime handles inference. This avoids a hosted inference API subscription, not the cost of computation.

Architecture

The frontend sends prompts to Ollama’s local REST API and displays the response. A browser-extension layer is the path for adding explicitly permitted page context. That boundary matters: a page should not be read or forwarded just because a chat window is open.

HTML / JavaScript · Ollama · DeepSeek / LLaMA · Local REST API

Project scope

The focus is a local browser chatbot and page-context integration, not a replacement for every cloud assistant. Once the runtime and model are installed, local inference need not rely on a hosted API; fetching new web pages still requires a network connection.

Tradeoffs

Ollama installation, model downloads, browser permissions, and local API access add friction. Response speed and usable model size depend on RAM, CPU, and GPU. Hardware, storage, and electricity still cost money, and local execution does not remove the need to secure the machine.

03

Smart Home Automation

Hardware-first / Local control & scheduling

Problem

Household appliances often sit behind separate controls and disconnected automation products. For Indian homes, an affordable central system could make everyday control simpler and make usage patterns easier to understand—without requiring every device to depend on a cloud service.

Approach

The design brings appliance control, monitoring, and scheduling into one local hub. A mobile UI provides manual control, while local inference is being considered for usage prediction and suggested schedules. Energy savings are a goal to measure, not an assumed outcome.

Architecture

An SBC-based hub, with a custom PCB as a hardware direction, connects over WiFi to relay modules controlling household devices. The hub holds control logic and local inference; the mobile interface communicates over the home network. Basic control should remain usable without a cloud connection.

SBC / Custom PCB · WiFi · Relay modules · Local inference · Mobile UI

Status & budget target

This is an in-development hardware direction. Under ₹10,000 for a household setup is a design target, not a verified build cost. The bill of materials, device count, installation, and protection requirements still need validation for Tier 1 and Tier 2 Indian homes.

Tradeoffs & next questions

Local control reduces cloud dependence but makes network recovery, safe relay states, and manual overrides essential. Electrical safety comes before prediction features. A possible move into small manufacturing is a separate concept with different reliability and safety requirements.
