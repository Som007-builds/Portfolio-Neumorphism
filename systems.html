01

Foretyx / Arbiter

Venture / AI security, governance & privacy gateway · Design & feasibility

Foretyx is my venture; Arbiter is its proposed product: a gateway that makes the decision to share data with a model explicit, inspectable, and policy-aware.

Design documented; product implementation not independently verified. No matching public source or runtime demonstration was established in this review.

Problem

Adding an AI model to an application creates another boundary for sensitive data. Customer records, employee information, and financial details should not reach an external model simply because they happen to be available to the application.

Approach

Arbiter would sit at an application’s model-call boundary, combining authorization with payload minimization. The first scope is one deliberately integrated application and one model adapter—not automatic protection for every AI tool an organization uses.

Proposed request lifecycle

  1. Intercept: accept a bounded request with trusted identity, role, purpose, and destination context from the application.
  2. Evaluate policy: apply a versioned allowlist for role, data, and model destination. Reject missing identity, unknown policy, or denied requests before any model call.
  3. Minimize: detect candidate PII, redact disallowed fields, and use scoped pseudonyms only where continuity is needed. Recheck the transformed request; uncertain cases stop.
  4. Call the model: send only the approved payload to the approved local or hosted adapter with a timeout. Return the response through the gateway; response inspection is a separate planned boundary.
  5. Audit & fail safely: record decision metadata for allow, deny, and error paths. Policy/filter failure stops forwarding; model timeout returns a controlled error with no silent provider fallback.

Proposed: request interception · Policy enforcement · PII redaction · Scoped pseudonymization · Metadata-only audit

Design decisions & tradeoffs
Detection accuracy vs. latency
Rules offer predictable cost but miss context; semantic detectors may improve coverage at additional latency and with false positives. Measure missed PII, over-redaction, and gateway overhead separately from model time.
Redaction vs. pseudonymization
Removal loses context. Stable pseudonyms preserve relationships but remain linkable and are not anonymization; keys, scope, retention, and access require explicit decisions.
Local vs. hosted processing
Local detection limits external disclosure but adds hardware and maintenance costs. Hosted detection itself crosses a data boundary; it must not receive raw sensitive data by default.
Fail-closed vs. availability
The proposed default is fail-closed on identity, policy, filtering, or required-audit failure, even if that interrupts a task. Fail-open would favor availability but permit unreviewed disclosure; it is not the default or a hidden fallback.
Policy & audit governance
Version policies, reject stale/unknown rules, and restrict who can change them. Log request ID, policy version, decision/reason code, destination alias, duration, and redaction counts—not prompts, responses, detected values, or raw identity. Limit access and retention; metadata can still be sensitive.

These are proposals, not production controls. A gateway cannot guarantee perfect detection, prevent all re-identification, or establish legal/regulatory compliance on its own.

Next milestone / Synthetic-data gateway

Build one policy evaluator, one deterministic redactor, a stub model adapter, and a metadata-only audit sink. Use fictional records only; keep real customer data out of the first prototype.

Future acceptance criteria—not test results: a permitted clean request reaches the stub once; a denied role/destination reaches it zero times; synthetic PII is removed from captured outbound payloads; missing identity, malformed input, stale policy, filter errors, and timeouts produce controlled failures. Audit-write failure must block forwarding. Verify allow/deny/error audit events contain no payload or sensitive fixture values.

Axion

Research intelligence / Claim-level knowledge graph · Working prototype

Axion turns scientific literature into a connected, inspectable graph of claims, evidence, contradictions, and research gaps — deliberately not a chatbot over PDFs.

Working self-hosted prototype in active development. The end-to-end loop (ingest → extract → reason → API → workspace) runs on a real corpus, but several capabilities are experimental and the evaluation set is still limited.

Problem

Scientific findings are not stored in a form that makes them easy to compare. A single question is answered in fragments across many papers, and two papers can agree on a topic while disagreeing on one specific, parameter-scoped result. Plain summaries often quote a conclusion without the paper, section, or sentence it came from.

Approach

Axion ingests papers from arXiv, extracts atomic structured claims (subject, metric, direction, confidence, evidence span, section), and stores them in a Neo4j property graph plus a ChromaDB vector index. It retrieves semantically similar claims, asks an LLM to judge their relationship (contradicts, supports, or unrelated), mines gaps, proposes experiments, and propagates confidence. A coordinator answers questions through a plan → retrieve → reflect → synthesize loop, and a six-view Next.js workspace lets a researcher inspect the graph, contradictions, gaps, timeline, and confidence drift.

Pipeline

  1. Ingest: fetch papers from arXiv and split the text into sections.
  2. Extract: pull up to eight falsifiable claims per section, each with provenance.
  3. Store: persist claims to the graph and embed them into the vector index.
  4. Reason: retrieve candidate claims and adjudicate relationships with an LLM.
  5. Synthesize: mine gaps, propose experiments, propagate confidence, and answer with citations.

Python · FastAPI · Neo4j · ChromaDB · Next.js / React · sentence-transformers

Design decisions & tradeoffs
Document-level retrieval vs. a claim-level graph
A graph is inspectable and supports cross-document conflict, but it depends on extraction quality and adds moving parts. Retrieval is only as good as the claims that were extracted.
LLM verdicts are hypotheses
A CONTRADICTS edge is a prompt to investigate, not a fact. The model can mislabel an unrelated pair, and a verdict without a shared subject and metric should be treated as uncertain.
Confidence propagation
Confidence is updated heuristically — a small bonus for supporting claims, a larger penalty for contradictions, clamped to a range. It is a ranking signal, not a calibrated probability.
Two stores, loose consistency
The graph and vector index are kept roughly in sync by ingestion code and are not transactional across both; a failure mid-ingest can leave them temporarily inconsistent.

Status / Evaluation

The loop runs on a real corpus, but several capabilities remain experimental. The current evaluation set contains only same-paper pairs that the production agent declines to compare, so it cannot yet measure production contradiction detection; the project reports macro F1 as the honest headline metric and states that limitation directly. It is a research prototype, not a production service.

Evidence & source

  • Self-hosted prototype with an end-to-end API, graph, vector store, and Next.js workspace.
  • Relationship verdicts and confidence are heuristic; evaluation is limited to the reported dataset.

Orion

Supervisory analytics / Air-gapped SOC assessment · SIH 2026 build

Orion is an air-gapped supervisory analytics platform that turns SOC operational evidence into explainable, evidence-linked hypotheses for examiners.

Built for Smart India Hackathon 2026 (problem statement 26157, NCIIPC). The project reports its backend suite passing and a working persisted validation path; it is a hackathon build, not a production security product.

Problem

SOC teams generate enormous operational evidence, but the supervisory signals that matter can be invisible in the reports built from it: critical alerts closed unusually fast, alerts acknowledged without real investigation, the same asset recurring without remediation, or systems producing unexpectedly little telemetry.

Approach

Orion ingests periodic batches of SOC evidence (alerts, cases, investigations, escalations, assets, telemetry, notes), validates and quarantines records, and scores them through a deterministic rules engine plus ML-assisted analytics: peer-relative anomaly detection, feature attribution, and investigation-note similarity. Output is a set of prioritized hypotheses, each linked back to its evidence as a finding card.

Design principles

  • Air-gapped: no external APIs, CDNs, or online inference.
  • Hypotheses, never verdicts.
  • NOT_ASSESSABLE is a valid outcome; missing evidence stays missing.
  • No silent drops: rejected records are quarantined and visible.
  • Append-only ledger; findings reproduce from their evidence.

Python · FastAPI · SQLite · DuckDB · Rules + ML analytics

Design decisions & tradeoffs
Hypotheses, not verdicts
Every finding carries its evidence so a reviewer can check it. The platform supports judgement; it does not replace it or claim to detect wrongdoing.
Exact anomaly evaluation vs. cost
Leave-one-out Isolation Forest scoring preserves semantics but fits a model per target, which limits very large detector workloads. The reported benchmark covers the streaming note path, not full detector throughput.
NOT_ASSESSABLE is not “low risk”
When the required evidence structures are absent, the honest answer is that the question cannot be assessed — not a green result.
Single-writer storage
DuckDB is single-writer, so ingestion and analysis run outside the request thread to keep the API responsive.

Reported validation

Project-reported: a passing backend suite, a streaming benchmark over 100,000 investigation notes, and a persisted RulesEngine path that produced real rapid-closure findings on synthetic data. Full detector throughput is deliberately not claimed, and no production or compliance result is implied.

  • Air-gapped FastAPI backend with a rules engine, ML analytics, quarantine, and an append-only ledger.

Indigent

Local-first agentic AI / Sovereign on-prem workbench · SIH 2026 build

Indigent is a sovereign agentic workbench: a system where the model, knowledge base, code execution, and audit trail all stay on one machine — and where the software can show that they did.

Built for Smart India Hackathon 2026 (problem statement 26117). The control plane, policy enforcement, sandbox, audit, and local retrieval are implemented and tested; P&ID production extraction and full multimodal transport remain in progress.

Problem

Industrial teams work with confidential information — P&IDs, inspection reports, SOPs, and vendor terms — that cannot be sent to a cloud AI service. The requirement is not “mostly local” but demonstrable control: proof that inference, retrieval, and execution stayed on the machine.

Approach

A request is classified, planned, and run through a bounded state machine (intake → classify → plan → retrieve → tool → verify → artifact → validate → approve → complete). Model output is treated as an untrusted proposal: every tool call is authorized by a deterministic policy validator and re-checked by the runtime before execution, and consequential deliverables wait for a named approver. Code runs only inside a Docker sandbox with --network=none and a read-only filesystem. A live Sovereignty Monitor reports external-call counters and can never display AIR-GAPPED while a counter is non-zero.

Stack

Next.js (same-origin proxy) → FastAPI → SQLite (WAL), Ollama for local models, Qdrant for vectors, and a Docker sandbox. Deliverables include DOCX, XLSX, and code packages with SHA-256 integrity manifests.

FastAPI · Next.js · Ollama · Qdrant · Docker sandbox · SQLite

Design decisions & tradeoffs
Local inference vs. hardware limits
Keeping inference on-machine avoids a per-request API dependency and keeps data local, but model size and latency depend on the hardware someone actually has.
Fail-closed vs. availability
A bounded, fail-closed design favors safety over convenience: if the sandbox is unavailable, the system fails loudly instead of falling back to a host subprocess.
Application-level sovereignty
The monitor and egress guard operate at the application layer. Host firewall, OS hardening, and network isolation remain deployment responsibilities, not guarantees of the software alone.
Honest empty state
When extraction or a model is unavailable, the default composition reports an empty result rather than fabricating an answer.

Status / Roadmap

The control plane, policy validator, sandbox, audit ledger, and local retrieval loop are implemented. Production P&ID graph extraction and full multimodal transport to a local vision model remain in progress. It is a hackathon build with a defensible core, not a hardened enterprise product.

Evidence & source

  • Local-first FastAPI + Next.js workbench with a policy-validated tool loop and a Docker sandbox.
  • Some capabilities are staged; the default composition reports empty state rather than inventing answers.
