Start with the data boundary

Design thinking / Early feasibility

Decide what information may leave an application before choosing a model. Filtering is one control, not proof of privacy.

The question before model quality

When I started thinking about useful AI products, I kept coming back to the data they would need. Healthcare records, employee information, customer PII, and financial transactions are not interchangeable with a public example prompt. Sending that information to a third-party model can raise legal, contractual, and ethical questions before model quality even enters the discussion.

That does not mean external models are always off-limits. It means the application needs an explicit answer to what may leave, for what purpose, and under whose authority. A proof of concept with sanitized dummy data does not establish that the same workflow is appropriate for real records.

A proposed boundary, not a guarantee

Foretyx is my venture; Arbiter is its proposed AI privacy and policy product. The design explores middleware that would check access policy and redact or tokenize personally identifiable information (PII) before an approved request reaches a model. The aim is to make privacy decisions visible in the request path rather than leaving them as assumptions inside application code.

Redaction is not the same as anonymization: remaining context can still identify a person. OWASP’s sensitive information disclosure guidance is useful here because it treats data minimization, access controls, and sanitization as complementary measures. A filter alone cannot establish who was allowed to retrieve the source record.

What would make the design testable?

I’m still defining the primitives and how to assess feasibility; these notes are design reasoning, not runtime proof. A gateway cannot promise perfect detection, eliminate re-identification risk, or establish compliance on its own. The next step would be a narrow flow using synthetic records: identify sensitive fields, state the policy, and inspect both the outgoing payload and the failure path.

That inspection would need to include logs and error messages, not just the model request. Moving a secret out of a prompt but into a diagnostic log would move the exposure rather than resolve it.

Entry 002 / Architecture Original note · April 2026 3 min read (estimate)

From proxy to policy

Design thinking / Proposed architecture

Authorize data use before constructing the prompt, then check the payload. A policy-update channel also needs explicit rules for stale state.

Authorization before transformation

The first Arbiter design I sketched for Foretyx was a simple proxy: receive a request, strip PII, forward it to the model, and return the response. That is an understandable starting point, and filtering remains useful. But it leaves an important question unanswered: should this user have been able to include that information in a model request in the first place?

The direction I’m exploring adds identity and access management (IAM) context before the request is constructed. A policy engine would evaluate the user’s role, the permitted data, the model destination, and the purpose of the request. The application could then build the prompt within those constraints, with filtering as a separate check rather than the entire security model.

That separates policy decisions from payload transformation. Access control asks whether information may be used; a PII filter asks whether sensitive information is still present. Neither replaces the other, and both need clear failure behavior. The design also needs to account for applications that cannot move policy checks earlier in their request flow.

Prompt injection is a separate concern from PII detection. As OWASP’s prompt injection guidance explains, untrusted documents or web pages can carry instructions. A model’s interpretation of that text must not grant new data access or tool privileges. Authorization belongs in deterministic application controls, not in a promise inside the system prompt.

Policy delivery is not policy consistency

A WebSocket-based policy push is one proposed way to distribute rule updates without redeploying every integration. It would not make updates instant or reliable by itself. Disconnections, missed messages, policy versions, acknowledgements, and stale cached rules all need a defined response. For sensitive requests, I would rather make the failure explicit than quietly continue with an unknown policy state.

MDN’s WebSocket documentation describes a two-way communication channel, not a policy protocol. I would need application-level version checks, authenticated updates, and a resynchronization path. Reconnecting should fetch an authoritative policy snapshot rather than assume no updates were missed.

Proposed checks, not executed results

  • Denied field: a synthetic record includes a field outside the caller’s role. The proposed check is that it never enters prompt construction, even if the PII detector would miss it.
  • Policy revoked: access changes between prompt construction and dispatch. The proposed check is to revalidate the applicable policy version before forwarding, with a defined rule for in-flight requests.
  • Disconnected client: cached policy expires while the update channel is unavailable. The proposed check is that sensitive requests stop with an explicit error until trusted state is restored.

This remains an architecture concept, not a deployed control plane. These checks describe evidence a future integration should produce; they are not gateway test results.

Entry 003 / Practice Original note · 2025 2 min read (estimate)

Systems before scripts

Learning note / Design habits

Sketch the request path, choose the smallest useful implementation, and use failure cases to challenge the architecture.

Sketch ownership and failure

Before jumping into code, I try to draw the path a user’s request will take. What does the user actually need? Which component owns the data? What breaks first, and what would be hardest to change later? Even a rough sketch can uncover a dependency that is easy to overlook inside a single function.

The point is not to avoid scripts or design a large system for every small task. A short script is often the right tool. The habit I want to build is understanding where that tool fits, which assumptions it makes, and what happens when those assumptions stop holding.

Let a small implementation push back

Architecture only helps if implementation can challenge it. I’m learning to move between a small working example and the wider picture: sketch a boundary, implement the narrow path, test a failure, and revise the design. Understanding syntax and understanding the system are complementary skills, not competing identities.

For a local control design, that means asking who owns a device’s state before adding a dashboard. What should happen if a scheduled command and a manual command disagree? What should a restart restore? Those questions identify decisions the code must express; they do not require a distributed platform to answer.

Separate a decision from its evidence

A useful design note records the assumption, the simplest choice, and what would make that choice wrong. A local controller might be a reasonable starting point for avoiding a network dependency. It would still need checks for restart behavior, conflicting commands, and safe defaults before I could claim reliable operation.

This is a learning habit, not evidence that those checks have passed. The case study records the intended boundaries; runtime behavior would need its own implementation and observations.

Entry 004 / Local AI Original note · 2025 2 min read (estimate)

The case for local models

Learning note / Inference tradeoffs

Local inference changes the data path and resource budget. It does not automatically make a browser workflow private, offline, or accurate.

Control over a different data path

Large hosted models get most of the attention, but running a DeepSeek or LLaMA model on a personal machine changes the questions I can ask. What can I build when the inference path stays local? Which tasks work well with a smaller model? How much control does a simple browser interface need to make that useful?

Local inference can avoid sending prompt content to a hosted model provider and remove the need for a per-request API subscription. It is not free computation. Model downloads take storage, inference uses electricity, and usable model size and response time depend on the available RAM, CPU, and GPU. A local setup also needs careful handling of logs, browser permissions, and the runtime’s network exposure.

Local is a configuration, not a guarantee

The official Ollama API documentation distinguishes local and cloud access. A local server address alone is not proof that inference stays on the device: the selected model and any cloud features also matter. The intended setup would use a downloaded local model and verify where requests go, without silently falling back to a hosted provider.

There is an offline advantage once the model and runtime are installed, but it has boundaries: a local model cannot fetch a new web page without a connection, and running locally does not make its answers correct. Hosted models still have useful capabilities and operational advantages. I’m exploring local models because they offer a different set of tradeoffs—not because one approach has already replaced the other.

A narrow local-first workflow to evaluate

A local-first workbench is a way to make those tradeoffs concrete: keep inference, retrieval, and tool execution on one machine, and treat every model proposal as untrusted until a deterministic check approves it. Page content and model output should remain untrusted input, not authority to reach outside the machine or invoke tools.

A useful evaluation would record the hardware, model, task, response time, and failure behavior with networking unavailable, and confirm that no request silently reaches a hosted provider. I’m not reporting benchmark results here. The goal is a workflow that is understandable on the hardware someone actually has, with a visible error when the local runtime cannot serve the request.
